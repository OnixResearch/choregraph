## Context

Choregraph evidence spans production Rust, Verus proofs, Nickel source observations, Kamacite canonical artifacts, Trellis references, and Lattice parity. Each layer has a different owner and claim strength.

## Success Contract

Completion requires one deterministic bundle that binds every required layer, independent verification of bundle linkage, release gates that fail on stale or skipped evidence, and a non-mutating publication candidate. A folder of unrelated passing logs or a hash without role validation is false completion.

## Bundle Roles

The release manifest contains stable roles for:

- source tree and license;
- canonical machine and lifecycle schemas;
- production core and built library;
- theorem source, theorem inventory, proof results, and trusted surface;
- Rust, Verus, solver, Nickel, Nix, and dependency identities;
- Kamacite machine, lifecycle, trace, exhaustiveness, source, and proof-reference carriers;
- positive and negative fixture corpus;
- execution-graph parity and Lattice downstream results;
- Cairn, Octet, traceability, and Nix receipts;
- Valence-friendly role projection and explicit non-claims.

Project-owned identities use BLAKE3. Interoperability fields preserve required external algorithms without replacing the project identity.

## Verification

Bundle verification rehashes every declared artifact, checks canonical roles, verifies receipt linkage through selected adapters, rejects undeclared required artifacts, and compares current policy, schema, proof, source, and toolchain identities.

A missing negative rail, skipped proof, stale fixture, wrong theorem set, mismatched source, unsupported Kamacite profile, or failed downstream check blocks readiness.

## Valence and Cairn Boundary

Valence links canonical identities, roles, spans, sidecars, and non-claims. It does not prove Choregraph behavior. Cairn evaluates lifecycle and evidence policy. It does not create source-code or theorem correctness.

The release bundle records those bounded roles instead of collapsing them into one broad verified label.

## Publication Candidate

The candidate records a proposed immutable source revision, source archive BLAKE3, license, acquisition adapter, package set, release bundle identity, and rollback baseline.

Candidate generation is read-only or writes local artifacts only. Publication, signing, push, remote authority changes, and endpoint deployment require separate explicit operator action and evidence.

## Downstream Handoff

The execution-graph compatibility change and Lattice adoption change must cite the accepted Choregraph source and bundle identities. Their own checks remain required. Upstream evidence does not prove downstream integration.

## Validation

The release rail runs formatting, tests, property tests, expected failures, Clippy, no-std targets, Verus, Nickel contracts, canonical corpus checks, adapter checks, parity, downstream tests, Octet, Cairn validation and gates, traceability, and Nix checks.

## Claim Boundary

A passing bundle proves exact presented identities, selected proof results, canonical linkage, and maintained check outcomes. It does not prove verifier soundness, compiler correctness, evaluator equivalence, event truth, authorization freshness, runtime effects, remote availability, or whole-product release eligibility.
